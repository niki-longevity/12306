# 12306Pro 测试

## 1. 测试环境

- **硬件**：4 核 8 线程，16GB 内存
- **部署**：所有服务、中间件、压测工具均在同一台机器
- **数据集**：981 趟车次模板，169 个站点，15 天排期数据
- **压测工具**：自编写的 Node.js 压测脚本（`bench.js`）

## 2. 查票性能

### 2.1 引入本地缓存前

每次查票请求 → Redis 逐个查询车次详情，IO 等待极高。

| 指标 | 数值 |
|------|------|
| QPS | 600 ~ 800 |
| RT 平均 | 280ms |
| P90 | 633ms |
| P95 | 550ms |

瓶颈：每个请求需要 N 次 Redis 往返（N = 匹配车次数），网络延迟累加。

### 2.2 引入 Caffeine 本地缓存后

静态车次信息缓存在 JVM 堆内，查票直接从本地内存读取。

| 线程数 | QPS | RT 平均 | P99 |
|--------|-----|---------|-----|
| 1 | ~3,000 | 3~6ms | ~8ms |
| 16 | 11,000+ | 5~7ms | ~20ms |

提升幅度：QPS 约 **15~18 倍**，延迟降低约 **40 倍**。

### 2.3 优化分析

本地缓存消除了 Redis 网络 IO。Caffeine 采用 `refreshAfterWrite=10min` 保证数据在 10 分钟内最多一次异步刷新，查询路径完全无阻塞。库存状态在购票成功后实时写穿更新，不存在 10 分钟延迟问题。

## 3. 购票性能

### 3.1 阶段一：同步远程调用

最初方案，购票成功后同步 HTTP 调用 order-service 创建订单。

| 指标 | 数值 |
|------|------|
| QPS | ~300 |
| RT 平均 | 41ms |
| P99 | 197ms |

瓶颈：购票线程等待 HTTP 响应 + 数据库写入完成。

### 3.2 阶段二：本地消息表 + Canal

通过 Outbox 模式异步解耦，Canal 监听 binlog 推送。

| 指标 | 数值 |
|------|------|
| QPS | ~900 |
| RT 平均 | 19ms |
| P99 | 66ms |

提升：异步化消除了 HTTP 同步等待，QPS 提升 3 倍。

### 3.3 阶段三：RocketMQ

替换 Canal 为 RocketMQ，消息可靠性更高，延迟消息原生支持。

| 指标 | 数值 |
|------|------|
| QPS | ~1,500 |
| RT 平均 | 11ms |
| P99 | 30ms |

提升：RocketMQ 比 Canal 链路更短，消息发送延迟更低。

### 3.4 最终方案流程

```
购票请求 → 责任链校验 → Token 桶限流 → 本地搜索空座
  → 双锁(本地+分布式) → Lua 原子扣减 → RocketMQ 异步
  → 立即返回"排队中"
```

购票主路径不等待订单落库，RT 仅包含 Redis Lua 操作 + MQ 发送（共约 10ms）。

## 5. 数据一致性测试

| 场景 | 验证方式 | 结果 |
|------|----------|------|
| Redis 位图缺失已售区间 | 订单落库时冲突检测 + 修复 | 自动修复 |
| 重复启动后模板数据 | INSERT IGNORE + UNIQUE 约束 | 不产生重复 |
| 窗口过期重启 | 追补逻辑验证（模拟 3 个月前窗口） | 正确追补 |
| 座位区间冲突 | MySQL UPSERT 检测 | 拒绝+回滚 |
