# 开发问题与解决方案

我在开发 12306Pro 的过程中遇到了一系列技术问题，从查票性能、库存表示、购票并发到数据一致性和容灾，每个问题都经历了多轮思考与优化。以下按时间线记录关键问题及其解决过程。

---

## 问题一：查票性能 — 从 Redis N 次往返到本地缓存

### 初始方案

查票流程：根据日期 + 出发站 + 到达站 → 查出所有匹配的车次编号 → 逐个去 Redis 查车次详情。

```
GET /ticket/list?date=2026-06-12&start=广州南&end=武汉站
  → Redis: LRANGE "2026-06-12:广州南:武汉站" 0 -1
  → 假设返回 15 个车次编号
  → for each code: GET "TrainStop:2026-06-12:G1001"
  → for each code: GET "TrainStop:2026-06-12:G1002"
  → ...共 15 次 Redis 往返
```

每个请求 15+ 次 Redis IO，查票 QPS 只有 600~800，RT 平均 280ms。

### 尝试过的方案

**方案 A：大 Key 合并存储。** 用一个 Key 存所有车次信息，避免多次往返。但计算后发现：15 天 × 981 个车次 × ~2KB 每个 = 约 30MB 数据，且库存更新会导致频繁的 JSON 序列化/反序列化，大 Key 问题严重，Redis 迁移和分片困难。不采纳。

**方案 B：Redis Pipeline 批量获取。** 将 N 个 GET 打包成一次 Pipeline，减少往返。测试过但效果不显著——Pipeline 的响应仍然需要等待最慢的那个 GET，整体延迟改善有限。具体数据已遗失，记忆中是约 40% 提升，远不够。

### 最终方案：Caffeine 本地缓存

认识到车次的**静态信息**（经停站、时刻、里程、车厢配置）极少变化，没必要每次从 Redis 取。将这些数据缓存在 JVM 堆内：

```
查票流程变为：
  1. Redis LRANGE 获取车次列表（1 次 IO）
  2. Caffeine 批量获取车次详情（0 次 IO，命中率 ≈ 100%）
  3. 从本地缓存读取区间库存状态
```

车次模板每天才变一次（凌晨 2 点推进窗口时），Caffeine 设置 `refreshAfterWrite=10min` 保证最终一致。余票状态在购票成功后实时写穿更新，不依赖 10 分钟刷新。

**效果**：单线程 QPS 从 600~800 提升到 ~3,000，16 线程 QPS 11,000+，RT 从 280ms 降到 5~7ms。

## 问题二：座位库存表示 — 位图方案

### 问题分析

12306 的座位不是单一商品，而是按区间拆分。一个座位可以卖给多个不重叠区间的乘客。如果用 Hash 结构（`{座位1: [区间1售, 区间2售, ...]}`），内存压力巨大：15 天 × 981 车次 × 8 节二等座 × 90 座 × 5 区间 ≈ 数百万个 Key，Redis 内存爆炸。

### 位图方案

每个车次的每种座位类型用一个二进制位图，每个座位在每个区间占 1 bit。一辆二等座车厢 90 座 × 4 区间 = 360 bits = 45 bytes。整个系统的位图总量极小：

```
15 天 × 981 车次 × 3 座位类型 × ~50 bytes ≈ 2.2 MB
```

### 行式 vs 列式

当前采用**行式**（先按座位排列）：同一座位的连续区间放在一起。好处是一次读取 1~3 个字节就能判断某座位在目标区间是否空闲。

未来可能的**列式**优化（先按区间排列）：所有座位在某一区间的占用状态连成一片，配合 `Long.numberOfLeadingZeros()` 指令，一次操作检查 64 个座位。但写入时需要 N 个区间各 1 次 Redis 操作，适合读多写少的场景。

## 问题三：位图搜索 — 从顺序搜索到随机起点 + 自适应熔断

### 初始方案：顺序搜索

从头扫描位图，找到第一个区间全空的座位。压测发现 QPS 随时间下降——越卖到后期，前面全是已售，无效搜索消耗大量 CPU。

### 优化一：随机起始位置

```java
int startPos = ThreadLocalRandom.current().nextInt(totalSeats);
for (int offset = 0; offset < totalSeats; offset++) {
    int pos = (startPos + offset) % totalSeats;  // 随机起点，环形搜索
    if (isSeatFreeInMemory(bitmap, seatStartBit, ...)) { ... }
}
```

避免了"扫到末尾全是已售"的退化，QPS 恢复到稳定水平。

### 优化二：自适应熔断

```java
int maxAttempts = (minStock < passengerCount * 3)
    ? Integer.MAX_VALUE   // 票少时不限制搜索次数
    : 100;                // 票多时限 100 次
```

票多时大概率前几次就命中，限制搜索次数防止无效 CPU 消耗。票少时放开限制，尽量帮用户找到票。

### 尚未解决的深层问题

每个请求仍然从 Redis 拉取完整位图。在高并发下，大量请求持有不同的位图快照，看到的占用状态不一致，导致 Redis 已经卖给别人的座位被重复尝试。我的设想是**本地位图缓存**——每台应用服务器固定负责一部分车次，Redis 修改后同步更新本地 copy，搜索直接读本地，避免每次拉取位图的网络开销和数据滞后。逻辑隔离下没有跨服务器脏数据问题，仅需处理本地多线程读写。

## 问题四：Token 桶限流的竞态与灵活性权衡

### 三个阶段

**阶段一：按座位数分发令牌。** 例如二等座 90 座就发 90 个令牌。但忽略了区间因素——90 个座位可以卖出 200+ 张票（不同区间组合）。

**阶段二：按区间数 × 座位数分发。** 例如 8 节 × 90 座 × 5 区间 = 3,600 个令牌。但高并发下竞态严重——放行了大量请求，到 Lua 层才因冲突失败，白白消耗服务器资源。

**阶段三：日常 vs 高峰期分场景。** 这是我的最终方案：

| 场景 | 策略 | 理由 |
|------|------|------|
| 日常 | 区间×座位数 | 并发低，竞态少 |
| 高峰期 | 固定 OD 对分配 | 减少无效竞争，牺牲灵活性换稳定性 |

### 未实施的设想

统一采用固定分发 + 分批放票：日常场景只开放一部分票，对每个 OD 对区间实时监控售票速度和剩余量，快售罄时再释放一批。固定分发的好处是可以直接把令牌数作为余票数展示，不必维护每区间的精确库存。这个方案会增加本地缓存压力，但全量 OD 对数据并不大，加上热点缓存策略，我认为总体收益可观。

## 问题五：数据一致性 — Redis 与 MySQL 的双层保障

### 问题

Redis 作为实时操作层，如果宕机且从节点未同步最新数据，新主节点存在脏数据（已被购买的座位标记为未售）。

### 方案：MySQL 真相源 + 冲突自动修复

订单真正落库时，MySQL `seat_bitmap` 表存储座位位图的权威版本。`OrderServiceImpl.create()` 执行 UPSERT：

```sql
UPDATE seat_bitmap SET bitmap = bitmap | mask
WHERE train_code=? AND date=? AND seat_type=?
  AND carriage_num=? AND seat_num=?
  AND (bitmap & mask) = 0  -- 仅当区间全空闲才更新
```

如果 `affected_rows = 0`，说明 Redis 有脏数据。此时对比 MySQL 位图与用户请求区间，执行冲突修复：

- **Dirty 区间**（MySQL 有标记但 Redis 没有）→ Redis 补标记
- **Clean 区间**（用户想买但 MySQL 已被占）→ Redis 回滚位图 + 归还库存 + 归还令牌

### 局限

这个方案保证最终一致性，但修复是**被动且分散的**——每次冲突修复一部分脏数据，无法一次性恢复全部。我还没有找到好的实时恢复方案。

## 问题六：容灾 — Redis 主节点 + RocketMQ 主节点同时故障

曾认真思考过极端场景：Redis 主节点和 RocketMQ 主节点同时宕机，且从节点均未同步最新数据，且 MySQL 也同时故障。

结论：这是一个概率极低的事件（可能比陨石撞地球概率还低）。工程上没有任何系统为这种全局级联故障做实时强一致保证——代价太大，全局同步的延迟和吞吐下降完全不可接受。

业界通用做法是组合防御：
- **半同步复制**：主节点至少等一个从节点确认后才返回
- **多环节留痕**：Outbox 消息表、订单表、位图表的交叉可对账
- **后期对账**：定时任务逐条比对 Redis 位图与 MySQL seat_bitmap，发现差异自动修复

我的项目目前做了 Outbox + 冲突修复，后期对账是下一步计划。

## 问题七：分布式锁优化 — 双锁机制

### 从单层到双层

最初只使用 Redisson 分布式锁，每个购票请求直接去 Redis 抢锁。后来在某开源项目（github搜12306）中看到一个更好的方案：先竞争本地锁，再拿分布式锁。

```
本地 ReentrantLock.tryLock(0) ──→ 失败 → 直接跳过，不访问 Redis
         │成功
         ▼
Redisson.getLock(key).tryLock(100ms) ──→ 失败 → 释放本地锁，跳过
         │成功
         ▼
    Lua 原子操作
```

好处：大量请求在第一道本地锁就被过滤，减少了 Redis 分布式锁的竞争压力和网络往返次数。

### 锁粒度选择

| 方案 | 并发度 | 评价 |
|------|--------|------|
| 按车次 | 1 | 太粗 |
| 按座位类型 | 3 | 仍然粗 |
| 按区间 | ~区间数 | 需多把锁，释放复杂 |
| **按座位（我的方案）** | ~座位数 | 简单高效，粒度刚好 |

我最终选择了座位级锁。进一步细分到区间锁带来的收益递减，而死锁和释放复杂度显著增加，不值得。

## 问题八：消息可靠性 — Canal 到 RocketMQ 的演进

### Canal 方案的问题

早期使用本地消息表（`ticket_outbox`）+ Canal 监听 binlog 推送消息到 order-service。但 Canal 有额外运维复杂度，且不支持原生延迟消息，关单需要自己实现定时轮询。

### RocketMQ 的好处

- 原生延迟消息：`syncSend(topic, msg, 3000, 16)` —— 第 4 个参数是延迟级别，16 对应 30 分钟
- 削峰填谷：订单创建异步化，购票线程不等待落库
- Producer/Consumer 分离：ticket-service 只管发，order-service 只管收，职责清晰

替换后 QPS 从 900 提升到 1,500，RT P99 从 66ms 降到 30ms。
